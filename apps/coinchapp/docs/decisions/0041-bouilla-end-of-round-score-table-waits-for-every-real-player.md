# 0041 — Bouilla end-of-round score table waits for every real player, capped at 6s

Date: 2026-08-17
Status: Accepted
Decision: The end-of-round score table ("Partie suivante") now only disappears once every non-bot player has pressed it, or 6 seconds have elapsed since the round ended - whichever comes first (`ROUND_AUTO_ADVANCE_MS` in `lib/bouilla/types.ts`). Online mode gained this gate for the first time (previously `nextDeal` advanced for everyone the instant any single player clicked); ad-hoc already waited for every human indefinitely and only gained the 6s cap. Local solo is unchanged/untimed (only one real player, nothing to wait for). The finished-match screen ("Nouvelle partie" rematch) is explicitly excluded from both the wait and the cap - it stays a fully voluntary action with no forced auto-rematch, confirmed with the user.
Context: User report that the online score table disappeared for everyone as soon as one player clicked "Partie suivante", without waiting for slower teammates; asked for a wait-for-everyone rule with a 6s hard cap so the table never gets stuck if someone walks away.
Rationale: Online had no readiness gate at all (`lib/server/actions-game.ts`'s `nextDeal` called `applyStartNext` unconditionally); ad-hoc already had the "wait for every human" half (`useP2PBouillaHost.ts`'s `ready` Set) but no timeout half. Tracking readiness for online required a place to persist "who has clicked" across the stateless Server Action calls between different players' requests - added as an optional `readySeats?: Seat[]` field on Bouilla's own `GameState` (persisted for free inside the existing `games.state` jsonb, no SQL migration) rather than a new `game_players` column, since it is pure per-round bookkeeping the rules engine already threads through `startNextRound`/`markReadyForNextRound`. The 6s cutoff reuses `games.turn_started_at` (already re-stamped to "now" on every `persistGame`, including the one that entered "scoring") instead of adding a second timestamp column. Excluded the finished screen from the timeout on explicit user confirmation: auto-starting a whole new match without every player's consent was judged a worse surprise than a slow player occasionally holding up "Partie suivante" for up to 6s.
Consequences: New `lib/server/bouilla-round-gate.ts` (`applyReadyForNextRound`, `advanceScoringTimeout`); new `readyForNextRound` Server Action, wired from `GameRoom.tsx`'s `bouillaActions.onNextRound` (Coinche's `onNextDeal` still calls the original unconditional `nextDeal`, untouched). `lib/server/view.ts`'s `buildView` now also computes `nextDealGate` for online Bouilla (previously ad-hoc only), reusing the same `NextDealGate` shape the client already rendered ("waiting for players X/Y"). Client-side, `BouillaTable.tsx` schedules a one-shot re-sync exactly at the 6s deadline (via the already-existing `onForceSync`, now passed as the stable `forceResync` reference instead of a fresh inline wrapper each render) so the cap does not have to wait on the slower 15s safety-net poll; `useP2PBouillaHost.ts` schedules its own equivalent local timeout. 2 new engine unit tests (134 total); typecheck/build/lint clean (pre-existing unrelated `useMatchStats.ts` lint error untouched).
Alternatives_Rejected: A `game_players.ready_for_next_round` DB column (rejected - would need a real SQL migration the user has to run manually against Supabase per `docs/RUNBOOK.md`, for state that is pure per-round bookkeeping already naturally expressed inside the existing `state` jsonb); a dedicated `scoringStartedAt` timestamp field (rejected - `turn_started_at` already gets re-stamped on every state-changing persist, including the entry into "scoring", so a second timestamp would be redundant); applying the same wait+cap rule to the finished screen's rematch too (rejected per explicit user confirmation - auto-starting a rematch nobody agreed to felt like the wrong default).
