# 0055 — Combined win/loss counter across all 4 games, shown in `HomeTopBar`'s settings panel

Date: 2026-09-17
Status: Accepted
Decision: Added `lib/client/matchResultStats.ts` (`getMatchResultStats()` / `useRecordMatchResult(matchId, finished, won)`), backed by one new `localStorage` key (`coinchapp-match-results`) shared by Coinche, la Bouilla, Président, and la Bataille Corse - one combined `{wins, losses}` counter, not one per game. Each game's own finished-match overlay (`DealOverlay`, `BouillaRoundOverlay`, `PresidentRoundOverlay`, `BataillecorseTable`'s `FinishedOverlay`) now calls `useRecordMatchResult` with its own already-computed "did I win the match" boolean and `gv.gameId` as the once-per-match dedup key (guarded via `sessionStorage`, not React state, so a page refresh on the finished screen never double-counts). Displayed in `HomeTopBar`'s existing settings panel (`myStats`/`winsCount`/`lossesCount`, FR/EN) - the same shared panel already used on every game's home splash, no new button per the "shared base" rule.
Context: Part of a cross-repo request (root `muchogames` + `tranquil` + this app) to add wins/losses stats to every card game. Root-repo investigation found `docs/PRODUCT.md`'s Out_Of_Scope explicitly listed "Comptes utilisateurs, statistiques persistantes, classement (pour l'instant)" - flagged to the user, who confirmed via an explicit question: stay client-only/per-browser (no real accounts), one combined counter for this app rather than one per game, displayed in this app's own UI (not synced back to the hub's `/profile`, which cannot reach this app's `localStorage` anyway - different origin).
Rationale: This app had no match-end win/loss concept in code before this (only the pre-existing, never-called `useMatchStats.ts` "funny awards" hook, and Coinche's per-*deal* `iWon` in `DealOverlay`, not per-*match*) - each game's finished overlay was read directly to find its own already-computed match-winner boolean (`view.winner === myTeam` for Coinche's team-based win; `iAmWinner`/`view.winners?.includes(mySeat)` for Bouilla/Président; `view.winner === gv.mySeat` for Bataille Corse) rather than inventing a new one. `gv.gameId` (the server-assigned match id, present in every mode - online, ad-hoc, local) was chosen as the dedup key over a `useRef`, since these overlays can remount on a page refresh while still showing the finished screen. `HomeTopBar` was the only real candidate for display: it is the one screen guaranteed to render on every game's home splash regardless of which of the 4 games was just played, matching "one combined stat", and already owns the one settings panel per screen this app allows.
Consequences: `DealOverlay` gained a required `gameId` prop (`GameTableScene` now passes `gv.gameId`) - the one new prop-threading needed since it, alone among the four, didn't already receive `gv`. `docs/PRODUCT.md`'s Out_Of_Scope line is now inaccurate for this one stat and needs a user-confirmed edit (not done in this same commit - asked separately, since `docs/PRODUCT.md` requires explicit confirmation before every edit). `npm test` (237/237), `npm run build` (Next.js typecheck), and `npm run lint` all pass with the same pre-existing baseline issues as before this change (`useMatchStats.ts`'s lint error, `DealOverlay`'s unused `contractMade` warning) - no new ones introduced; the new `settingsOpen`-gated read in `HomeTopBar` needed the same `eslint-disable-next-line react-hooks/set-state-in-effect` precedent already used elsewhere in this app for a post-hydration `localStorage` read.
Alternatives_Rejected: One counter per individual game (Coinche vs Bouilla vs Président vs Bataille Corse tracked separately) - rejected by the user in favor of one combined counter. Syncing this back to the hub's `/profile` page - rejected, this app is a different origin from the hub and cannot reach its `localStorage`; would have needed a new one-way "game → hub" channel this app doesn't have. A real backend/account system so stats survive a cleared browser or follow the player across devices - rejected by the user as disproportionate for a stat display, and out of scope for this app's documented "no accounts (for now)" stance without its own separate decision.
