# 0067 — La Bataille Corse: figure/ace tribute-filler slap exception removed entirely

Date: 2026-09-26
Status: Accepted (supersedes the remaining half of 0056, after 0066 already removed its sandwich half)
Decision: `detectSlapPattern` (`lib/bataillecorse/pattern.ts`) no longer has any figure/ace-filtered branch at all. It is now just the plain double/sandwich test on the real, unfiltered pile. A challenge-rank card that answers a tribute always opens a brand new tribute (full attempt count for its own rank) - it is never compared, for slap purposes, against the card that opened the tribute it just paid off, even when its rank happens to match.
Context: User reported a live match: `P0` opened a tribute with `A♥`; `P1` burned 3 plain attempts (`7♠, 9♣, 10♦`), then answered with `A♦` - which both paid off `P1`'s tribute and opened a fresh one for `P0`. `detectSlapPattern`'s figure-filtered double check (0056) treated `A♥`/`A♦` as adjacent once the plain fillers were ignored, so `P1` slapped and won the pile. User's explicit correction: "si J1 joue un as, on repars sur 4 cartes" - playing an ace to answer a tribute just restarts the cycle at a fresh attempt count, full stop, no slap tied to it.
Rationale: Given how `resolveTributeEffect` works - every challenge-rank flip unconditionally opens a fresh tribute, regardless of whether one was already owed - the card that closes any tribute (by playing a new challenge-rank card) is *by construction* always simultaneously the card that opens the next chain. There is no other shape the figure-filtered double check could ever match: the two figures either open/close the same single tribute (now explicitly disallowed) or are unrelated across multiple resolved chains, in which case the second-to-last filtered card is provably the opener of the chain the last card just closed (same argument). So the filtered branch had no case left it could legitimately fire for once 0066 already removed its sandwich half - removing it outright, rather than special-casing "except when it's the same tribute", is the actually-simplest form of the same fix and matches the user's plain-English rule. A 1-filler gap between two same-rank challenge cards still fires as a literal, unfiltered sandwich (`A, x, A`) with no special-casing needed - only 2+ real fillers in between now yield no slap.
Consequences: `pattern.ts` collapsed to a single ~10-line function, no more `detectOnSequence`/`detectDouble` split. `pattern.test.ts`: the "figure double across a tribute chain" test now asserts `null`. `engine.test.ts`: the equivalent `submitFlip` test now asserts no `slapWindow` opens and the fresh tribute is owed back to the other seat instead. `RulesModal.tsx` FR/EN copy rewritten to state the reset behavior instead of a filler-skip exception. `npm test` (305/305), `npx tsc --noEmit`, `npm run build` pass; `npm run lint` shows only the pre-existing unrelated `useMatchStats.ts` baseline issue.
Alternatives_Rejected: Keeping a narrower fix (exclude only the specific opener/closer pair of the *same* tribute, but still allow a filtered double across genuinely separate, already-resolved chains) - rejected after confirming via the tribute state machine that this second case is structurally unreachable (see Rationale), so the narrower fix and the full removal are behaviorally identical; the full removal is simpler code.
