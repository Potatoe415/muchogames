# 0068 — La Bataille Corse: a tribute failure defers to a real slap window first

Date: 2026-09-26
Status: Accepted
Decision: When a flip both exhausts a tribute's last attempt AND completes a double/sandwich on top of the pile (e.g. the failing card matches the card already on top), `submitFlip` no longer awards the pile to the tribute challenger immediately. It opens the pattern's real, full `SLAP_GRACE_MS` slap window first (`GameState.pendingTributeWinner` records the challenger as the fallback). Either seat can genuinely slap it during that window and win it as a `"slap"`; if nobody claims within the grace period, `resolveStaleSlapWindow` falls back to the original automatic `"tribute"` award.
Context: User reported a live match ending in `P1 wins 17 cards (failed tribute): ... Q♠ 9♠ 9♣` - the last two cards (`9♠, 9♣`) form a literal double, but the pile was swept instantly as a tribute failure with no chance for either side to actually slap it. User's request: keep a delay before pocketing in exactly this case, so a coinciding double/sandwich still gets a real chance.
Rationale: The existing slap-window/grace-timeout machinery (`SlapWindow`, `attemptSlap`, `resolveStaleSlapWindow`) already does exactly what's needed for any other slap - reusing it (rather than a purely cosmetic client-side display delay with no real slap capability behind it) means a genuine claim from either seat, including a bot's simulated reflex, is handled identically to every other slap: same race resolution by `reactionMs`, same UI, no new code paths on the client at all. A new `pendingTributeWinner` field (deliberately not exposed in `PlayerView`/`redact.ts` - purely an internal engine bookkeeping value) is the minimal state needed to remember what to fall back to if the window goes unclaimed.
Consequences: `types.ts`: `GameState` gains `pendingTributeWinner: Seat | null` (always `null` outside this exact scenario; treated as `null` via `?? null` wherever read, so a persisted match from before this change - `undefined`, not `null` - degrades safely). `engine.ts`: `submitFlip` now checks for a pattern before an immediate tribute award; `awardPile` clears the field on every pile award (a real slap always wins over the pending fallback); `resolveStaleSlapWindow` applies the fallback once the window closes unclaimed. `test-utils.ts`'s `stateWith` gained the same optional field. New tests in `engine.test.ts` cover: the window opening instead of an immediate award, the fallback firing when unclaimed, and a real slap during the window winning instead. `npm test` (308/308), `npx tsc --noEmit`, `npm run build` pass; `npm run lint` shows only the pre-existing unrelated `useMatchStats.ts` baseline issue. No `PlayerView`/client changes needed - a pattern-driven slap window already renders and resolves identically regardless of why it opened.
Alternatives_Rejected: A separate, shorter (e.g. 2s, as literally suggested) client-side-only display hold with no real slap capability - rejected, it would show the cards longer but a tap during that time would still be evaluated as a false slap (no `slapWindow` open), which is worse than today, not better. A distinct, shorter grace constant just for this case - rejected as unjustified inconsistency; reusing `SLAP_GRACE_MS` keeps one single, already-tuned "how long does any slap opportunity stay open" constant.
