# 0031 — Colocate `coinchapp` and `tranquil` into this repo via `git subtree` (V2 of the earlier "refonte")

Date: 2026-09-17
Status: Accepted
Decision: Imported `coinchapp` (Next.js/React/TypeScript, 97 commits) and `tranquil` (its own npm-workspaces monorepo: `shared`+`client`+`api`, 38 commits) into this repo at `apps/coinchapp/` and `apps/tranquil/` via `git subtree add`, preserving each repo's full commit history rather than squashing or copying files fresh. Root `eslint.config.mjs` and `.prettierignore` now explicitly ignore `apps/**`. **Deployment was not touched**: both Vercel projects still build from their original standalone GitHub repos; `hub-config.json`'s launch URLs are unchanged. The original `coinchapp`/`tranquil` GitHub repos will be archived once (and only once) Vercel is repointed to build from `apps/` here — that repoint is deliberately deferred as its own step (see `docs/BACKLOG.md`).
Context: Direct follow-up to the 2026-09-17 "refonte" decision above, which scoped V1 to this repo only and deferred "V2: fold in `coinchapp`/`tranquil`" until concrete. User asked to do that now. Clarifying questions up front (colocate-only vs. full deployment unification; preserve history vs. fresh copy; archive vs. keep the old repos) were answered: colocate only, preserve history via `git subtree`, archive the old repos once done.
Rationale: Inspecting both repos first changed the plan from what the original monorepo article implied — `coinchapp` and `tranquil` are full Next.js/React/TypeScript stacks (`tranquil` is even its own nested npm-workspaces monorepo), not vanilla JS like every other game here. Actually unifying their build with this repo's Vite/vanilla-JS setup would mean picking one framework and rewriting the other — far beyond "migration" and directly contradicting `docs/TECH.md`'s "No UI framework" line. "Colocate only" (same Git repo, each app keeps its own independent build/deploy) is exactly what Vercel's own monorepo support (`rootDirectory` per project) is designed for, and is the only interpretation consistent with `AGENTS.md`'s "no speculative architecture" / "smallest coherent change" rules. `git subtree` (not `--squash`) was used over a fresh file copy so `git blame`/history on the imported code survives, and over `git submodule` because a submodule keeps the code in a *separate* repo/checkout — the opposite of "colocate for one LLM context". Verified each app still builds cleanly from its new nested path (`npm install && npm run build` for `coinchapp`; `npm run build:shared && npm run build -w client` for `tranquil`) before considering the import done, and confirmed root `npm run check` stays clean (the initial run surfaced 236 files `.prettierignore` needed to exclude before it was added — expected, since these apps were never meant to follow this repo's formatting).
Consequences: This repo now contains three genuinely different stacks under one Git history: vanilla JS (`public/`, root), and two independent Next.js/React/TypeScript apps (`apps/`). `docs/TECH.md`'s Stack_Frontend line was scoped to clarify it describes the hub-spoke surface only. `AGENTS.md` gained a rule that `apps/<name>/` follow their *own* `AGENTS.md`, not this repo's. Root `npm install`/`lint`/`format`/`build` do not touch `apps/**` (no root `workspaces` field was added, by design — the three stacks stay fully independent, no shared `node_modules`/dependency resolution). `apps/coinchapp/package-lock.json` picked up an unrelated pre-existing drift fix (lockfile said `0.9.1`, `package.json` said `0.9.6`) as a side effect of the verification `npm install`. Both original GitHub repos are untouched and still the live deployment source — nothing changes for players yet. Next, separate step: repoint each Vercel project's Git source to this repo with the matching `rootDirectory`, verify a preview deployment, then move the production domain over, only then archive the original repos.
Alternatives_Rejected: Full deployment/build unification into one Vercel project — rejected, would require rewriting one of three frameworks into another, far riskier than the user's "migration" ask. `git submodule` — rejected, keeps the code physically in another repo/checkout, defeating the "one LLM context" goal. Squashed history (`--squash`) or a fresh file copy — rejected, user explicitly asked to preserve history. Repointing Vercel / archiving the old repos in the same pass — rejected, that is a live production cutover (domains, build source) that deserves its own explicit go-ahead and live verification, not something to bundle into a local Git operation.
