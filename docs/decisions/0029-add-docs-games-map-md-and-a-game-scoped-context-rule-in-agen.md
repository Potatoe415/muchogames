# 0029 — Add `docs/GAMES_MAP.md` and a game-scoped-context rule in `AGENTS.md`

Date: 2026-09-17
Status: Accepted
Decision: Added `docs/GAMES_MAP.md`, a one-page index of every game (id, folder or external deploy, kind, main-file sizes, which `shared/CONTRACT.md` modules it uses, whether it has its own `NOTES.md`). Added a "Game-scoped work" subsection to `AGENTS.md` Section 1 requiring: consult the map before opening `public/games/`/`public/data/`, scope reads/edits to one game's own folder plus its `hub-config.json` entry unless the task explicitly spans several games, prefer `shared/CONTRACT.md` over shared source, and read a game's own `NOTES.md` (once it has one) before its main source for small edits. `docs/TECH.md` Architecture_Principles gained one bullet naming this as a formal convention. `docs/GAMES_MAP.md` was added to the `AGENTS.md` File Ownership table as a living document.
Context: Direct follow-up to the `engine.js`/`CONTRACT.md` work above. User asked explicitly: future games worked on with an LLM must stay well-isolated, minimize token consumption while staying high quality, and there should be a "map" read up front so an agent only touches the games/components a task actually needs.
Rationale: The existing `AGENTS.md` Startup Protocol already scopes *which docs* to load by task type, but had no equivalent for *which game folder* to touch — an agent doing a Yatzy task had no documented reason not to also open Millionaire's `app.js`. A map (rather than e.g. `.cursorignore`-ing inactive games) was chosen because it is additive, needs no per-session maintenance, and doesn't block legitimate cross-game work (e.g. touching `shared/`) the way a blanket ignore would. Sizes/shared-deps were measured directly (`Get-Content | Measure-Object -Line` per file, `grep` for `shared/js/`/`PlayerProfile`/`GameHeader` usage) rather than guessed, so the map starts accurate. Retroactively writing a `NOTES.md` for every existing oversized game (`millionaire`, `pyramide`, `yatsy`, `diceduel`) was deliberately left out of this pass — the user's ask was forward-looking ("if I add games in the future"); the map already flags which existing games are oversized, and their remainder is tracked in `docs/BACKLOG.md`.
Consequences: New games must get one row in `docs/GAMES_MAP.md` and, once they cross ~150–200 lines, a `NOTES.md`. `docs/GAMES_MAP.md` will drift if a game's shared deps or size class changes without updating it — same maintenance risk as any other living doc, mitigated by the same discipline already applied to `docs/BACKLOG.md`/`STATE.md`. Found and flagged (not deleted) one pre-existing piece of dead code while building the map: `public/games/pictionary/index.html` + `main.js` are orphaned — Pictionary actually launches via `wordplayer.html?game=pictionary`, not this folder.
Alternatives_Rejected: `.cursorignore`-style hard blocking of "inactive" game folders — rejected, too blunt (blocks legitimate cross-game/shared work, and "inactive" changes session to session, unlike a stable map). A single flat list with no per-game detail — rejected, doesn't tell an agent whether a `NOTES.md` exists or which shared modules are in play, so it wouldn't actually save a read. Writing `NOTES.md` for all existing oversized games now — rejected as out of scope for a forward-looking request; can be done on request per `docs/BACKLOG.md`.
