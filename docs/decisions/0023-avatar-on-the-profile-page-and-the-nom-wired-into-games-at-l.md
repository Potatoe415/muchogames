# 0023 — Avatar on the profile page, and the "Nom" wired into games at last

Date: 2026-09-06
Status: Accepted
Decision: `/profile` gained an Avatar (file upload, resized/compressed client-side on a canvas to roughly 50 KB, stored as a base64 JPEG in a new `localStorage` key `bergamots-player-avatar`). A new canonical module, `public/shared/js/player-profile.js` (plain global script, `window.PlayerProfile`), is the single reader/writer for both the name and avatar keys, used by the profile page and by Yatzy. Yatzy (`public/games/yatsy/`) gained its first-ever name input ("Ton nom" on the splash screen), pre-filled from the profile and applied to the local seat only — both in local pass-and-play/robot mode and online, where `serializeGameState()`/`hydrateFromRemoteGameState()` now carry each seat's name so the opponent sees the real name instead of the fixed "Player 1"/"Player 2" defaults. `hub.js`'s `appendLangParam()` became `appendLaunchParams()`, forwarding the profile name as a `?name=` URL param on every external game launch (Coinche, Bouilla, Tranquil today), the same mechanism already used for `?lang=`, since those apps run on other origins and cannot read Bergamots' `localStorage`.
Context: User asked for a richer profile (Nom + Avatar) and for the name to be usable across Coinche, Bouilla, Yam (Yatzy) and Tranquil, with a documented contract so any future game follows the same pattern, and with the explicit requirement that everything keeps working identically for a player who is not authenticated.
Rationale: An avatar image is too large to travel through a URL, so it stays Bergamots-only (profile page only) — propagating it cross-origin would need a backend/hosted-image piece not asked for here. The name, being a short string, reuses the existing `?lang=` URL-param precedent for cross-origin apps instead of introducing a new transport (postMessage, shared cookie domain, backend) for a single field. `player-profile.js` is a plain global script, not an ES module, because Yatzy's scripts are all classic `<script src>` includes (see `game-header.js` for the established pattern) — an ES module would not be usable there. `auth.js` (root-level, bundled by Vite, cannot reach files under `public/` at build time) keeps its own duplicated name-key constant per the 2026-09-05 decision, but now also exports `getStoredPlayerName()` for `hub.js` to call, avoiding a second duplicate of that logic. Every consumer only *pre-fills* its own existing input — Coinche/Bouilla/Tranquil already had their own pseudo fields, reused instead of replaced — never overwriting a value the player types, and never requiring one: an absent name/avatar reproduces exactly today's behavior (empty field, or Yatzy's translated defaults), independent of Google sign-in.
Consequences: `bergamots-player-avatar` is a new, Bergamots-only client-side key (no propagation, no backend, no `DATA_MODEL.md` change — same category as `bergamots-player-name`). Yatzy's `game_state` payload (Supabase `yatzy_games.game_state` jsonb) now also carries `players[].name`; well under the existing 64 KB cap, no schema change. Coinche/Bouilla (`coinchapp`) and Tranquil (separate repos, `dev-projects/coinchapp` and `dev-projects/tranquil`) needed their own small changes (pre-fill their existing pseudo `useState` from `?name=`) and got their own decision entries in their own `docs/DECISIONS.md`, per their own `AGENTS.md` protocol.
Alternatives_Rejected: A shared backend/profile API so any origin could fetch the name and avatar by some identifier — rejected as disproportionate (new persisted data, new infra) for a "pre-fill a text field" feature with no accounts. Auto-filling the avatar from the Google account's picture claim, mirroring the existing name auto-fill — deferred, not asked for, would add an external image fetch/CORS concern for a feature that is upload-only today.
