# 0020 — Show the signed-in email and add a placeholder profile page

Date: 2026-09-05
Status: Accepted
Decision: `auth.js` now decodes the `email` claim out of the Google JWT credential (client-side only, no signature verification, since nothing trusts this value for access control) and stores it in `localStorage` (`bergamots-auth`, replacing the earlier boolean `"in"` flag) so the popover can display it and it survives a reload. The popover also gained a "Profil" link to a new placeholder page (`public/profile/`, same unbundled static-page pattern as `public/admin/`) that shows no information yet. The login icon moved to the right of the language switcher (rightmost element), and both widgets got explicit `z-index` (`.auth-widget` above `.lang-switcher`) so the auth popover always paints in front instead of being covered.
Context: User asked to see the connected email in the popover and to add a profile menu opening an (for now empty) profile page, plus fixed the icon ordering and a stacking bug where the popover could render behind the language flags.
Rationale: This directly supersedes part of the same-day decision above ("no personal data ... no email ... stored"): the user explicitly asked for the email to be visible, which requires keeping it somewhere across a page reload since Google's credential is only delivered once, at sign-in time. `localStorage`, client-side only, stays the smallest solution — still no backend, no cookie, nothing sent to any server. `docs/PRODUCT.md`'s Out_Of_Scope was updated to describe this precisely instead of claiming zero personal data.
Consequences: The signed-in user's email is now the one piece of personal data the app keeps, entirely client-side, visible only to that browser. `/profile` follows the `/admin` convention: clean URL in production (Vercel), but `/profile/index.html` under `npm run dev` — no `vite.config.js` change needed.
Alternatives_Rejected: Re-deriving the email on every popover open via a fresh Google prompt — worse UX (would re-trigger Google UI) for no benefit over reading the already-decoded value. Storing the full ID token instead of just the email — more data than needed for a display-only status.
