# 0019 — Google Sign-In status widget on the hub, client-only

Date: 2026-09-05
Status: Accepted
Decision: Added a login icon top-right of the hub (`auth.js`, `#auth-widget` in `index.html`, styles in `hub.css`) using Google Identity Services (`https://accounts.google.com/gsi/client`) loaded client-side, hub-only. On successful sign-in, only a boolean flag is stored in `localStorage` (`bergamots-auth`); the Google JWT credential is never decoded, verified, or sent anywhere. No backend endpoint, no new Vercel env var, no Supabase table. Logging out clears the flag and calls `disableAutoSelect()`; it does not attempt to revoke the Google session itself. For now the flag has no effect on any game.
Context: User asked for a minimal Google-only login/logout status on the hub's home screen, explicitly requesting the least possible amount of information stored, with zero change to game behavior.
Rationale: A pure client-side status avoids a backend, a session store, and any personal data at rest — the smallest solution that satisfies "just a login status". Google's OAuth Client ID is not a secret (same convention as the already-public Supabase anon key in `public/games/yatsy/supabase-config.js`): it is restricted by Authorized JavaScript origins, not by secrecy, so it is committed directly in `auth.js` rather than passed through a Vercel env var.
Consequences: `docs/PRODUCT.md` Out_Of_Scope no longer claims "no player accounts/authentication" — replaced by "no accounts beyond an optional, information-less Google login status". `docs/TECH.md` Authentication section now documents this client-only flow alongside the existing admin-password auth. Google preview-deploy URLs (random per-PR `*.vercel.app` domains) are not in the Authorized JavaScript origins list, so the button will not render/work on Vercel previews — only on `localhost:5173` and `bergamots.vercel.app`. The real `GOOGLE_CLIENT_ID` in `auth.js` must be created by the project owner in Google Cloud Console (external step, not something an agent can do) and pasted in to replace the placeholder.
Alternatives_Rejected: Supabase Auth (already have a Supabase project) — would create real user records in `auth.users`, more infrastructure than "just a status" requires. A server-verified session (decoding/verifying the JWT in an `api/` function, issuing a cookie) — unnecessary complexity since no game or endpoint needs to trust this identity for anything.
