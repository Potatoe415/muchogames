# 0026 — Delete previously-flagged dead weight; start splitting `yatsy/app.js` via `storage.js`

Date: 2026-09-09
Status: Accepted
Decision: Deleted the ≈16.9 MB of dead files the 2026-08-30 audit had identified but left for the user to review (`old1.jpg`, `old2.jpg`, `old3.jpg`, `public/assets/banner-games-hub-old.jpg`, `public/games/millionaire/questions_{en,es,fr}.json`, `public/games/easyfrog/style.css`, and the two byte-identical dead copies of `shared/js/dom.js` / `public/shared/js/dom.js`), after re-confirming zero references repo-wide. Also extracted `public/games/yatsy/storage.js` (`window.YATZY_STORAGE`) out of `app.js`: every function that only reads/writes raw `localStorage` (rule settings, the reverse-dice/extra-roll boolean preferences, the online-session payload, the hub language reader) now lives there; `app.js` keeps the domain knowledge (key names, value shapes, `cloneRuleSettings` validation) and calls into `STORAGE.readJSON`/`writeJSON`/`readBoolean`/`writeBoolean`/`remove`/`readHubLanguage`.
Context: User asked for a status check on modularity, duplication, and documentation freshness, then asked to act on four specific findings: fix a stale line count in `docs/BACKLOG.md`, delete the already-identified dead weight, deduplicate `dom.js`, and start splitting `yatsy/app.js`.
Rationale: The dead-weight deletion had no open question left — it was fully audited and zero-reference on 2026-08-30, and the review step the user wanted was this conversation. For `app.js` (2267 lines against the 300-line project limit, still under active development), a full decomposition was judged too risky to do in one pass: there is no automated test suite, the game is a live real-time multiplayer app, and the two largest remaining blocks (rendering, and online-sync/session handling) call back into each other (render attaches click listeners that call handlers; handlers call render()), so splitting them cleanly needs an explicit shared context object, not a mechanical cut. The `localStorage` layer, by contrast, has zero coupling to rendering or handlers, matches the existing per-concern file convention already used by `diceduel/js/storage.js`, and was verified end-to-end in a live browser (solo game, dice roll, settings toggle, correct `localStorage` keys) plus `npm run lint`/`format:check`/`build` before landing.
Consequences: `public/games/yatsy/index.html` gained one `<script src="storage.js">` tag, loaded before `app.js`. `app.js` is now 2204 lines (from 2267) — still far over the 300-line limit; `docs/BACKLOG.md` Later now describes the remaining split (rendering block, online-sync/session block) as its own follow-up work, not "done". No `DATA_MODEL.md` change: the `localStorage` keys and their shapes are unchanged, only which file contains the `getItem`/`setItem` calls.
Alternatives_Rejected: Splitting `app.js` fully to ≤300 lines in this pass — rejected as too risky without test coverage on a live multiplayer game; scoped down to the one genuinely low-coupling layer. Leaving the dead weight for a separate future review — rejected, the user explicitly asked for it to be cleaned up now, and it had already been fully audited.
