# 0030 — Add `docs/NEW_GAME.md`, wired into `AGENTS.md` Startup Protocol

Date: 2026-09-17
Status: Accepted
Decision: Added `docs/NEW_GAME.md`, the single checklist for adding any game (technical: file location, `hub-config.json` schema, size limits, `data-id`, i18n, verification steps; visual: `game-header.css`/`game-header.js` chrome, `base.css` tokens, the hub tile's 4∶5 `object-fit: cover` crop). `AGENTS.md`'s Startup Protocol table now routes "task creates a new game" to it directly, and `docs/GAMES_MAP.md`'s own "Adding a new game" section was trimmed to point here instead of duplicating the steps.
Context: Direct follow-up to the `docs/GAMES_MAP.md` work above. User clarified the goal: when they ask an LLM to build a new game in the future, the platform's technical *and graphic* conventions should apply automatically, without having to be restated each session.
Rationale: `docs/GAMES_MAP.md` already told an agent *where* a game lives; it did not tell it *how* to build one consistently with the rest of the catalog. Grounded the visual section in what the codebase actually does today rather than inventing a spec: grepped every game's `index.html` for which shared stylesheets it loads (`game-header.css` universally, `base.css` in most but not all — `millionaire`/`cafards`/`diceduel` opt out for a custom skin, confirmed deliberate not accidental), and read `hub.css` to find the real tile-image contract (`.game-tile__media { aspect-ratio: 4/5 }` + `object-fit: cover`), rather than guessing a thumbnail size. Flagged, not silently fixed, that `data-id` (an existing `AGENTS.md` rule) is only actually present in `yatsy` today — a new game must still follow it.
Consequences: A single source of truth exists for "add a game"; `docs/TECH.md`'s config-over-code bullet and `docs/GAMES_MAP.md` both point to it instead of restating it. Drifts if a shared convention changes without updating this file too — same living-doc discipline as the rest of `docs/`.
Alternatives_Rejected: Folding this checklist into `docs/GAMES_MAP.md` directly — rejected, that file's job is indexing/context-isolation (read on every game-scoped task), while this one is a one-time build checklist (read only when creating a game); merging them would make the common case (editing one existing game) load a much longer file for no benefit. Enforcing the visual rules via a lint rule or template generator — rejected as premature tooling for a project with no bundler on most games; a checklist an agent reads first achieves the same outcome today.
