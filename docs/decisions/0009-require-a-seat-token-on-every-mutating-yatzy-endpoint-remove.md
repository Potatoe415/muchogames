# 0009 — Require a seat token on every mutating Yatzy endpoint, remove client-triggered bulk purge

Date: 2026-08-30
Status: Accepted
Decision: Deleted `api/yatsy/games/purge.js` and made seat-token proof mandatory on the two remaining unauthenticated mutating paths: `DELETE /api/yatsy/games/[code]` now requires a matching `role` + `resumeToken`, and `POST /api/yatsy/games/[code]/join` on a room whose status is already `playing` requires the caller to present the token for the seat they are reclaiming instead of being handed a fresh one. Added a 64 KB type-and-size guard on the `gameState` accepted by `PUT .../state`, and replaced the `innerHTML` template in `buildWinnerBanner` with `textContent` DOM nodes.
Context: A security audit requested by the user found that any anonymous caller could (a) wipe every row of `yatzy_games` with a single `POST /purge {"olderThanMs":1}`, (b) delete any room knowing only its 3-letter code, and (c) take over a seat in a game in progress, rotating the sitting player's token and kicking them out. Room codes are 3 letters (17,576 combinations), so the "capability" gating these endpoints was enumerable in seconds. The user chose to fix security first, to keep codes at 3 letters, and to preserve resume-by-code while requiring the token.
Rationale: `purge` was pure redundancy - the hourly `pg_cron` job in `0001_yatzy.sql` already hard-deletes rooms older than 48h - so deleting it removes an entire attack surface at zero functional cost, which beats authenticating it. For `join`, the legitimate "I closed my tab and came back" case was already served by `POST /resume` with the token persisted in `localStorage`; the client now forwards those same credentials when joining a code it already holds, so the user-facing flow is unchanged while anonymous seat takeover is gone. Deriving `localPlayerIndex` from the authenticated role (`creator` = 0, `joiner` = 1) also fixes a latent bug: the removed code assigned the seat of whoever's turn it was, contradicting its own comment claiming it replaced the inactive seat.
Consequences: `POST /join` on a room already `playing` now answers `409 game-in-progress` unless valid credentials are supplied - the `game-in-progress` error code and its FR/EN/ES copy already existed in `i18n.js` and `setSplashError`, so no translation work was needed. A player who loses their `localStorage` (cleared storage, different device) can no longer re-enter a game in progress at all; previously they could, by taking over a seat. `YATZY_MATCHMAKING.PURGE_AFTER_MS` and `YATZY_CONFIG.matchmaking.purgeAfterHours` are gone. `sw.js` `CACHE_NAME` was bumped to `yatzy-offline-v13`, without which returning players would keep running the cached pre-fix client. `GET /api/yatsy/games/[code]` remains unauthenticated and still exposes room state to anyone knowing the code - read-only, left open deliberately, logged as an Open_Question rather than changed outside the agreed scope.
Alternatives_Rejected: Keeping `purge` behind a shared secret or a Vercel cron header - rejected as redundant with `pg_cron`; less code beats more config. Lengthening room codes to 4-5 letters to make enumeration impractical - explicitly declined by the user for now, since codes are typed by players and rate limiting is the planned mitigation. Closing `join` on `playing` rooms outright (no reclaim at all) - rejected by the user, who wanted resume-by-code preserved. Full schema validation of `gameState` - rejected as premature: a type-and-size guard removes the storage-abuse risk without hardcoding the Yatzy state shape in the API, and rendering is now escaped at the sink anyway.
