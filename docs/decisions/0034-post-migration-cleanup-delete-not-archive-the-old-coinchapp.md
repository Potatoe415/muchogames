# 0034 — Post-migration cleanup: delete (not archive) the old `coinchapp` GitHub repo; delete the old Vercel project; rename `coinchapp-monorepo` → `coinchapp`

Date: 2026-09-17
Status: Accepted
Decision: Deleted the old, now-domainless `coinchapp` Vercel project via API. Renamed `coinchapp-monorepo` to `coinchapp` (the name was free once the old project was gone); `coinchapp.vercel.app` verified still 200 after the rename (a project rename does not touch its attached custom/vercel.app domains). The `Potatoe415/coinchapp` GitHub repo is being **deleted**, not archived — this reverses the earlier same-day decision (in the "colocate `coinchapp`/`tranquil`" entry above) where the user chose "archive" for both original repos. Deletion is a manual step for the user: the agent has no `gh` CLI available and deliberately did not extract the git credential stored in Windows Credential Manager to do it via the GitHub API, for the same reason the Vercel token is being treated carefully — extracting a secret the agent was not directly handed is a bigger overreach than using one the user pasted themselves.
Context: User asked to "clean up, delete what's no longer used" right after the `coinchapp` Vercel migration was confirmed live. Agent asked three explicit clarifying questions before touching anything, since one candidate (the GitHub repo) contradicted a standing decision: delete-vs-archive for the repo, delete-vs-keep-dormant for the old Vercel project, and whether to clean up a test game (`room_code = 'JQW'`) created in production Supabase during the live verification. User answered: delete the Vercel project, delete (revised) the GitHub repo, delete the test row.
Rationale: The old Vercel project had zero remaining purpose (no domain, no traffic could reach it) and Vercel project deletion, while irreversible, has no data/history value to preserve (unlike a GitHub repo's commit history) — safe to delete outright via API. Renaming `coinchapp-monorepo` → `coinchapp` was flagged as a nice-to-have back when the temporary name was chosen (naming collision with the old project); doing it now removes a source of the exact confusion that triggered the "why coinchapp-monorepo and not bergamots" question earlier in this session. The GitHub repo's commit history already lives on inside `bergamots` (imported via `git subtree`, full history preserved — see the original colocation decision), so unlike a from-scratch deletion, nothing is actually lost by deleting the standalone repo: its history survived the migration by design. The Supabase test row could not be deleted by the agent — `public.games`/`game_players` have RLS enabled with **no policies**, so only `service_role` can write (confirmed by reading `apps/coinchapp/supabase/migrations/0001_init.sql`), and the agent was never given that key (nor should it ask for it, having just flagged the risk of secrets in chat). The same schema already has a 48h TTL cleanup cron (`cleanup-expired-games`), so the row self-expires regardless; the user was given the one-line SQL to run themselves if they want it gone sooner.
Consequences: `docs/GAMES_MAP.md`/`STATE.md`/`BACKLOG.md` no longer need to track the old Vercel project. `Potatoe415/coinchapp` GitHub repo deletion and the `JQW` row cleanup remain open, user-side manual items in `docs/BACKLOG.md`. This decision does not change anything for `tranquil` — its original repo/Vercel project are untouched and still live, and no decision was made here about whether its eventual old-repo disposition will also be "delete" instead of "archive" (ask again when that migration is done, don't assume the revision carries over silently).
Alternatives_Rejected: Extracting the Windows Credential Manager git token to delete the GitHub repo via API — rejected, the agent surfacing a secret it was not explicitly handed for this purpose is a different (worse) risk profile than using a token the user pasted directly. Leaving the old Vercel project dormant "just in case" — rejected by the user; it had already been superseded and verified, so keeping it added no safety margin. Asking the user for the Supabase `service_role` key to delete the test row via API — rejected, that repeats the exact chat-secret-exposure risk already flagged this session for the Vercel token, for a single non-urgent cleanup row that already self-expires.
